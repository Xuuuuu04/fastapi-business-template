# 项目检查

## 选择检查范围

下面的命令在 `server/` 目录执行：

```bash
# 只调试一个包：最快，只检查这个包
uv run dev check --quick --module 模块名
# 几个包一起改：一次检查，公共部分只检查一遍
uv run dev check --module A --module B
# 按和 origin/main 的差异，自动找出受影响的包
uv run dev check --affected --base origin/main
# 日常完整范围检查（相同源码与环境可沿用结果）
uv run dev check
# 交付检查：强制执行，不沿用结果或模板工具验证
uv run dev check --database sqlite --delivery
# 按类别检查，或限定进程总预算
uv run dev check --group flow --workers 4
# 完整双库交付检查，只能使用已授权的隔离数据库
uv run dev check --database both --postgres 测试数据库地址 --delivery
# 审查完框架改动后，更新框架摘要
uv run dev framework-lock --update
```

怎么选：

- `--quick` 只用于一个包内的调试，它不能证明几个包放在一起也是对的。
- 改动涉及多个包时，用 `--module` 一次列全。`--module` 和 `dev finish` 的代码风格、格式和质量规则只看所选包的源码、测试、接口和业务文档，别的包已有的问题不会卡住本包；类型检查和生成文档仍然查全部，完整检查和交付检查看全部文件。
- 改了公共代码，或不确定影响哪里，跑完整检查。
- 整批交付和发布前，跑完整范围的 `--delivery` 检查；局部或分组通过不能代替交付。
- 生产使用 PostgreSQL 时加上 `--postgres 测试数据库地址`，只能用已授权的隔离数据库。
- 浏览器、容量、部署是另外的检查，按各自任务单独做，这个命令不包含。

## 业务检查、交付检查与沿用

业务检查用于开发中的反馈。`--group` 可选 `pure`（纯计算）、`module`（包）、`flow`（组合流程）、`framework`（公共框架）；省略时检查全部组。风格、类型、文档等公共检查仍执行，分组仅选择测试。

`--database sqlite|postgresql|both` 选择测试库；默认 `auto` 在提供 `--postgres` 时选择双库，否则 SQLite。PostgreSQL 必须显式提供隔离测试控制地址，不读取生产地址。`--workers` 是总测试进程预算，默认按 CPU 数量减二、至少二个、最多四个设置；双库总预算至少六个时 PostgreSQL 约占三分之二，否则平分预算，`0` 表示串行。实际预算和各库进程数写入检查记录。长样例提前分配，生成器副本的小范围检查使用串行。调度只改变顺序，不改变全部断言或交付范围；副本依然执行真实完整测试，不把类型增量缓存作为成功证据。

默认检查可沿用相同源码、范围、框架指纹、实际依赖和测试环境下的最近成功记录，并输出“沿用检查”，不会生成新的执行证据。目前按整个范围沿用；改动后范围内重新执行。产品里如果模板工具自己的文件（各 Skill 的 scripts 和 server/devtools）与 template-source.json 记录一致，默认省略模板工具自身回归，并明确显示“模板工具未改动，沿用模板验证”；业务测试、公共运行安全测试不省略。改业务、依赖、迁移、框架运行代码或测试配置都不影响这一点；模板仓库本身、改过模板工具、显式 framework 分组都运行这些测试。

`--delivery` 禁止沿用，重新执行所选范围，并检查交付规则与实现状态；模板工具测试是否省略和上面的条件相同。交付证据必须注明实际范围和数据库；SQLite 通过不代表 PostgreSQL 已验收。

## 业务现状过期

文档检查也会核对 `.agents/records/business-state/模块名.md` 的生成部分：源码或依赖版本、声明发生了变化，生成超过 24 小时，或者摘要与同名 JSON 不一致，都会报错。check 只做比较，不会自动刷新。处理顺序是：先读手写判断并更新下一步，然后显式运行 `uv run dev business-state`；需要真实运行状态时，在确认当前数据库和授权后加 `--runs`，否则保持未知。`dev docs` 可以初始化或更新过期的声明状态，但不读取数据库，不能代替业务验收。迁移含定时或长流程时，完成条件是先用 operations drill 按真实规模跑通整条链、核对产物和回放覆盖情况，再补局部细节。

## 框架摘要

`server/framework.lock` 记录公共代码、检查配置和项目 Skill 的内容摘要，防止它们被顺手改掉。

- 做业务时不要改这些文件。
- 确实要改，先看实际差异，写明用途和影响，再用 `uv run dev framework-lock --update` 更新摘要。
- 服务启动只检查运行必需的公共文件，部署时不需要带 Skill。

## 写测试的要求

- 预期结果来自业务文档里确认过的样例。旧系统的输出只能用来比较兼容性，不能当作正确答案。
- 和时间有关的样例：在操作执行时传入时间，或使用可控的时钟。不要在模块导入时就算好有效期，也不要为了让测试通过而放宽业务时限。
- 权限测试使用真实的应用权限。
- 事务、并发、外部操作结果未知、重启后恢复，按这项业务的风险程度来覆盖。

## 检查失败时

先读自动附带的中文运行报告，判断失败属于哪一类：

1. 代码实现有错。
2. 测试本身安排错了。
3. 缺少真实的数据来源。
4. 功能还没做。

当前业务和公共安全问题修复之后，才能说当前目标完成。其他交付条件单独列出来，不要悄悄并入当前阶段。

## 记录

每次检查都记下：代码版本、数据库类型、实际运行的命令和结果。完整检查失败之后，不能用之后一次局部检查的成功去覆盖它。

查询额度在公开的 contract 里声明 QueryBudget；显式声明后，测试超额默认失败，旧的未声明操作只警告。APP_QUERY_BUDGET_MODE=warn 可以临时只警告；逐项迁移完成后改成 error，让默认额度也在测试中报错。生产环境只记录。接入方法和测量含义见 server/shared/db/README.md。

命名检查的来历和删除条件见[检查说明](references/check-rationale.md)；没有当前替代证据时，不因为耗时或以前通过而删除检查。
