# 业务文档

[business.md](business.md) 说明谁使用产品、做什么、遵守哪些规则、数据从哪里来，以及对应的包和操作。完成业务的 Agent 对照代码改动更新这份文档；具体实现直接读代码，不重复抄写。

## 查业务

1. 先读 business.md，找到这项业务和它的包、操作。
2. 要找到代码，在 `server/` 执行：

   ```bash
   uv run dev locate --query "业务词或旧接口路径" --limit 10
   ```

   它在操作名、标题、别名、字段含义、表名、步骤标题、路由和定时里搜索，输出 JSON，带源码位置；只读本地代码，不连数据库。
3. 要看模块怎样协作、操作怎样执行：`/api/system/modules`（包之间的调用关系）、`/api/system/flows/{操作名}`（操作内部的步骤图）、`/api/system/runs/{运行编号}`（一次真实运行）。命令和权限见 fastapi-operations。
4. 查实现位置和调用入口时以代码为准；已确认的业务规则以用户的决定为准。两者冲突时用样例核对并报告差异，不把规则改成错误实现来让测试通过。

## 更新业务文档

什么时候更新：一项业务做完并提交之后；包的拆分合并、规则变化、接口变化、外部依赖变化提交之后。和用户确认过的规则，可以在写代码前先记进“规则”。

1. 看 business.md 第二行“已对照到提交”，记为 `X`。写的是“无”时，跳过第 2 步，直接读 `server/service` 下的代码。
2. 看这段时间改了什么：

   ```bash
   git log --oneline X..HEAD
   git diff X..HEAD -- server/service server/library server/app/api server/migrations
   ```

3. 宿主支持子代理时，派一个子代理做这一步：把差异范围 `X..HEAD`、business.md 的路径和下面的写法交给它，让它直接改 business.md 并交回改了哪几节。不支持子代理就自己做。
4. 按差异改文档，每项业务一节，写法见下表。只写这次差异真正改变的业务事实，没变的不动。
5. 把第二行改成当前提交号，和文档改动一起提交。子代理改的，先对照差异抽查一两处再提交。

| 写什么 | 怎么写 |
| --- | --- |
| 谁用、做什么 | 一两句话，用业务的说法，不用代码名 |
| 规则 | 确认过的业务规则，一条一行，带固定编号、具体数字和单位，附上确认过的样例和测试路径 |
| 数据 | 从哪里来、存到哪里、给谁用 |
| 包和操作 | `包名.操作名`，和代码里的名字一致 |
| 外部依赖 | 调用的外部系统和大模型，写系统名和用途 |
| 待定 | 还没和用户确认的规则，写清在等谁定什么 |
| 迁移状态 | 迁移旧系统的业务才写：已实现、联合检查通过、旧页面可用、已正式切换 |

不记录开发过程、修改历史和代码片段；历史从 Git 查看。一项业务删除了，就删掉它的一节。文档超过 400 行时，按业务拆到本目录下的 `business/业务名.md`，business.md 只留一览表和链接；这些文件和 business.md 一样属于产品，升级框架不覆盖。
