# 业务文档

记录产品的业务规则与操作入口，让业务状态和规则在文档里看得见、不用靠记。

## 查业务

1. **先读业务文档找包和入口**。打开 [business.md](business.md) 找到目标业务、包名和对应操作，只查现状，不要先看代码猜规则。
2. **用 `dev locate` 定位源码位置**。在 `server/` 执行以下命令按业务词或旧接口路径搜索（只读本地代码，不连数据库）：

   ```bash
   uv run dev locate --query "业务词或旧接口路径" --limit 10
   ```

3. **查模块关系与执行链路**。需要了解包间依赖、内部步骤或单次运行结果时，查询 `/api/system/modules`、`/api/system/flows/{操作名}` 和 `/api/system/runs/{运行编号}`。
4. **以确认过的规则为准**。代码实现与已确认规则不一致时，用业务样例核对并直接报告差异，不要把规则改成错误实现。

## 更新业务文档

一项业务做完、拆分合并包或变更规则与接口后执行：

1. **读取上次对照的提交号**。看 [business.md](business.md) 第 2 行“已对照到提交”的值 `X`；如果写着“无”，直接读取 `server/service` 下的源码，跳过第 2 步。
2. **查看区间代码差异**。在仓库根目录运行以下命令，只核对这次真正改变的业务事实：

   ```bash
   git log --oneline X..HEAD
   git diff X..HEAD -- server/service server/library server/app/api server/migrations
   ```

3. **按固定栏目更新文档**。如果当前工具支持子代理，可派子代理按 `X..HEAD` 修改后由你抽查核对；下线的功能同步删掉对应小节，超过 400 行时拆到 `business/业务名.md`。
4. **回填当前提交号并提交**。把 [business.md](business.md) 第 2 行更新为当前提交号，随文档改动一起提交。

| 栏目 | 写法要求 |
| --- | --- |
| 谁用、做什么 | 用一两句业务语言说清，不列代码类名 |
| 规则 | 一条一行写清固定编号、数字与单位，附上测试路径 |
| 数据 | 写清来源、存储位置和下游去向 |
| 包和操作 | 写 `包名.操作名`，与代码声明保持一致 |
| 外部依赖 | 列出调用的外部系统、大模型及用途 |
| 待定 | 列出尚未确认的规则及等待谁拍板 |
| 迁移状态 | 迁旧系统时标注：已实现、联合检查通过、旧页面可用、已正式切换 |

## 验收

[business.md](business.md) 第 2 行提交号已对齐 `HEAD`，新增或变更业务的规则、包名与测试路径均已补全，且文档中未夹杂开发流水账或代码片段。
