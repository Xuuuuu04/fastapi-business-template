# 文风与术语约定

这份约定管两件事：一是这个项目里所有写给人看的文字（Skill、README、自动生成的文档、运行报告），二是生成这些文字的代码里的固定文案。目标只有一个：**读的人一遍能懂**。信息一条不少，但要用完整、自然的中文说出来，不追求省字。

判断一份文字合不合格，用这一个标准：一段话拿给第一次接触项目的人，他不用回头读第二遍，就能知道发生了什么、接下来该做什么。

## 一、句子怎么写

**每句话有主语，一句话只说一个意思。** 需要表达几个意思时，分成几句写，用句号结尾，少用分号把短句串成串。

写法对照：

| 不要这样写 | 要这样写 |
| --- | --- |
| 登记不等于业务完成；未知不等于未运行，观察不是业务验收。 | 操作登记进了系统，只说明代码里有了它，不代表业务已经完成。查不到运行记录时写"未知"，但未知不等于没有运行过。观察到一次成功，也不能代替业务验收。 |
| 生成部分由命令维护：模块、普通/分段任务、流程、定时入口、最近运行、逾期与待确认。 | 生成部分由命令维护，包含六类信息：模块概况、后台任务（普通和分段两种）、多阶段流程、定时入口、最近的运行情况、逾期和待确认事项。 |
| 摘要会列出：计划里缺的部分、待确认的事、各数据库的检查版本、问题预览。 | 摘要会列出四类信息：计划里还缺什么、哪些事在等人确认、各个数据库的检查是什么版本、当前有什么问题。 |

**警告和限制写成完整的话，说明对象和原因。** 不要只留下一个否定句让人猜指的是什么。

| 不要这样写 | 要这样写 |
| --- | --- |
| 局部检查不代替全量检查。 | 局部检查只能证明改过的部分没问题，不能证明整个项目放在一起仍然正确。要证明后者，需要跑完整检查。 |
| 不要吞掉异常。 | 不要用 try/except 把异常吞掉再返回空值或零。出错时应该让异常正常抛出，这样错误会留在运行记录里，排查的人才能看见。 |

**面向 Agent 的信息和面向人的信息分开。** 文件路径、函数名、行号、JSON、编号这类内容，放进表格或代码块，并说明它是什么；不要混进正文的句子里。图里只放看流程需要的信息，明细一律放图下方的表格。

## 二、词汇怎么选

用最常见的中文词。避免这几个词：阻断、巡检、巡查、红线、门禁、判官，以及生僻的四字成语堆砌。技术名词第一次出现时，用一句话解释它是什么，之后再单独使用。

英文只在三种情况下保留：命令和参数名（如 `dev docs`）、代码里的标识符、行业通用的缩写（如 SQL、CSV）。除此之外的英文句子要翻译成中文，尤其是自动生成的内容（例如接口文档里的状态码说明）。

业务编码（如来源编号 1019）在文档里出现时，后面必须跟上含义，写成"1019（库存导出）"这样的形式。含义来自字段的 `meaning()`，没有含义的编码先补含义，再进文档。

## 三、术语表

这些词在整个项目里只用这一种说法，解释也统一。新文档遇到这些概念时，直接使用，不再另起名字。

| 术语 | 含义 |
| --- | --- |
| 登记 | 把模块、操作或任务写进系统的公共目录。登记之后系统才知道它的存在。 |
| 声明 | 代码里明确写出的信息，例如某个步骤读写哪些字段、对应哪条规则。文档和图都从声明生成。 |
| 操作 | 一个完整的业务动作，例如"创建联系人"。操作是模块对外的服务单位。 |
| 步骤 | 操作内部的一步。每个步骤做一件事：计算、读数据、写数据或调用别人。 |
| 流程 | 把步骤按顺序连起来形成的链条。 |
| 多阶段流程 | 有多个阶段的长流程，每个阶段有自己的事务和恢复点，例如"采集、等待、汇算、发布"。 |
| 检查 | 用 fastapi-check 跑的质量验证，包括风格、类型、结构、文档和测试。 |
| 验收 | 业务上确认"这个东西能用了"。检查通过不等于验收，验收需要人按业务标准确认。 |
| 业务现状 | 每个模块一份的本机档案，记录它现在的状态。分成两部分：生成部分（命令维护）和手写部分（开发者维护）。 |
| 生成部分 | 业务现状里由命令自动维护的内容，例如有哪些操作、最近是否运行。 |
| 手写部分 | 业务现状里由人写的判断：业务判断、外部依赖、下一步。 |
| 计算图 | 从代码声明画出的流程图，表示"按设计应该是这样"。 |
| 运行图 | 一次真实运行留下的执行图，包含实际用时和结果，表示"实际是这样发生的"。 |
| 查询额度 | 一个操作允许的查询次数、行数和数据量上限，在声明里写明，防止失控的循环查询。 |
| 来源批次 | 从外部系统或旧系统取来的一批数据，带编号，可供追溯。 |

## 四、自动生成的内容怎么排版

**图。** Mermaid 流程图的节点只放三样东西：序号、业务标题、类型（用颜色区分，图例放在图下方）。规则编号、函数名、文件位置、读写的字段、查询额度，全部放在图下方的"步骤明细"表格里，一个步骤一行。这样图负责讲清楚"流程怎么走"，表格负责讲清楚"每一步的细节"，各做各的事。

**表格。** 单元格里放短语，不放大段解释。同一种长解释（例如业务错误的文字说明）在一份文档里只展开一次，其他位置只写代号。表格上方加一行说明，讲这张表每一列是什么。

**状态和数据。** JSON 不直接进正文；需要保留原始数据时，放进代码块并注明来源。数字带上单位和含义，例如"1000 次查询""6400 万字节的返回内容"。

**文档开头。** 每份自动生成的文档在标题后写两三句：这份文档讲什么、由什么生成、在哪里写业务含义。读者靠这几句定位自己。

**空状态。** 模板还没有业务模块时，生成文档的业务部分是空的。要在空的位置写一句"当前还没有业务模块，新建模块后这里会自动出现内容"，不要留下没有解释的空表格。

## 五、状态怎么说

这个项目严格区分几种状态，文字表述必须准确，不能为了好听把一种说成另一种。语义保持不变，但要用完整的话说出来：

| 状态 | 准确的说法 |
| --- | --- |
| 未知 | 没有查到证据。未知不等于没有发生过，只是当前没有证据。 |
| 待确认 | 这件事需要人来决定，决定之前不要自己补业务含义。 |
| 过期 | 证据是旧的（源代码或声明已经变了），不能再拿来引用，需要重新生成。 |
| 检查通过 | 本次检查真实运行过并且成功。通过只对本次范围有效。 |
| 已验收 | 业务上确认能用。测试通过不等于验收。 |

## 六、写完之后自查

改动涉及文字时，交出去之前过一遍这五个问题：

1. 每句话有主语吗？一句话是不是只说了一个意思？
2. 有没有为了让检查通过而写的话术，而不是把事实讲清楚？
3. 面向人的句子里，有没有混进只有 Agent 需要的信息（路径、行号、JSON）？
4. 术语和术语表一致吗？业务编码带含义了吗？
5. 第一次读的人，能不回头读第二遍就看懂吗？
