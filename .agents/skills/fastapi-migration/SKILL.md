# 业务迁移

## 目标和做法

每次迁完一项用户能检查、能使用的业务，并保留已经确认的行为。

- 默认由一个代理从头负责：理解业务、写代码、改数据库、做联合检查。只有用户或项目规则明确要求时才分给多个代理。
- 不清空已有成果，不整批搬函数，不把迁移变成全面重写。

## 开始一项业务

1. 读旧系统里这项业务的入口、调用关系、规则、样例，以及新系统里已有的成果，并记下读的是旧系统的哪个版本。
2. 列出用户的操作和对应的旧接口，选出最小的完整业务。例：经营日报 = 读取订单 → 计算 → 保存并发布 → 旧页面查看和下载。
3. 在现有任务记录里写清楚：
   - 数据从哪里来；
   - 应得的结果；
   - 页面上的操作；
   - 需要哪些业务包和接口；
   - 需要哪些数据、权限、事务检查；
   - 完成条件；
   - 这次不做什么。
4. 条件确认后保持稳定。中途发现新问题，说明它是否影响当前业务。确实要扩大范围，就讲清依据和代价，不要悄悄把最终交付的要求并进当前阶段。

先稳定当前业务必需的表、应用权限、约束、事务和启动。不需要等所有业务表、完整的数据清理、容量测试和恢复演练都做完，才开始验证这一项业务。这些仍是正式交付前必须完成的，各自保留并继续推进。

依赖顺序只用来安排这一项业务内部的工作，不能变成"全项目一层一层做"。

## 怎样处理旧函数

| 旧函数的情况 | 怎么处理 |
|---|---|
| 正确、独立，只接收数据并返回计算结果 | 只迁当前业务用到的函数，放进本业务的 `steps/`，由正式步骤调用 |
| 查库、用 Session、请求外部、计算、提交混在一起 | 拆开：读取和外部动作放 `store/`，计算放步骤，保存交给新的事务安排 |
| 重复、没用、这期不需要 | 不迁 |
| 已知有错，或拆开比重写还贵 | 单独说明规则有什么变化，按确认的样例修复或重写 |

迁进来的计算函数不能再读全局配置、访问数据库、调用网络或偷偷写文件。步骤声明输入和输出字段，结果写回流程的工作数据，这样计算仍然出现在流程图和运行记录里。

旧数据表单独定义在 `server/legacy/`，只通过存储里的只读入口使用，不放进新库的迁移。完整例子见 [日报迁移样板](references/report-example.md)。

## 联合验证

含定时或长流程的迁移，完成条件是：先用 `fastapi-operations drill` 在隔离库按真实规模打通从定时首入口到发布的整条链，再补局部细节。使用录下来的上游原始响应回放，不访问真实系统；记录每阶段耗时、实际行数、最慢SQL、内存峰值、是否需要人工，以及回放和未覆盖阶段。配置与命令见 [系统操作](../fastapi-operations/SKILL.md)。只有样例规模、模拟模型或未覆盖的外部写操作不能算真实业务已验收；原件来源未知时明确标未知。

尽早把数据来源、计算、保存和旧接口放在同一份代码里验证。每次记下：提交编号、迁移版本、配置、实际使用的应用角色、输入数据来源。

- 各个包单独通过，不能代替放在一起运行的结果。数据库升级后，之前的验证记录就过期了。
- 不要先长时间分包开发、最后集中合并，也不要建一堆没人维护的分支和工作目录。

## 比较新旧结果

- 用固定的输入比较新旧输出。金额、单位、空值、缺失值、边界、异常都要有明确预期。旧结果本身对不对，要看业务规则。
- 外部写操作可以用"记录并确认"代替真实写入来验证，但真实数据来源是否完整、旧页面能否使用，要分别说明。
- 比较两份 OpenAPI，在 `server/` 执行：

```bash
uv run python ../.agents/skills/fastapi-migration/scripts/run_migration.py compare_api --before /旧/openapi.json --after ../doc/api/openapi.json
```

接口比较只比较声明，不能证明页面能用。要把旧页面接上，真正完成生成、查看、下载。返回"未就绪"的占位接口不算已迁移。

- 测试过期、数据库权限错、测试配置缺功能：先修测试的安排，不能放宽金额、时间或权限规则。
- 必须一起成功的动作放在同一个事务里，例如调价确认和商品占用。记录失败的情况不能阻塞业务事务。

## 记录和汇报

每项业务分四个状态记录，并附当前版本和证据：

1. 已实现
2. 联合检查通过
3. 旧页面可用
4. 已正式切换

还没拿到真实数据来源、身份或环境的，保持"未验证"。不要写精确的或估算的迁移百分比。汇报先说：用户哪个操作现在能做、结果是什么、卡在哪里。

## 正式切换

- 迁移期间，外部写操作只由一套系统执行；验证时用替代服务。结果不明的先查清楚，不要重复写。
- 切换前完成适用的容量、恢复、清理保护、权限和部署检查，写明怎么切换、怎么撤回。上线需要用户单独确认授权。
- 第一项业务可用之后，再扩大范围。
