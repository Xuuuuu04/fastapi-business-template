# 业务迁移

目标是每次完成一项用户能检查、能使用的业务，保留确认行为。默认由一个代理持续负责业务理解、实现、数据库变化和共同版本检查；多代理只在用户或适用项目规则明确要求时使用。不清空已有成果，不全量搬函数，不把迁移自动变成全面重写。

## 开始一项业务

先读旧业务入口、调用、规则、样例与现有成果，固定旧版本。列用户操作与旧接口，选最小完整业务，例如经营日报的来源读取→计算→保存发布→旧页面查看下载。

在现有任务记录中写清输入来源、应得结果、页面操作、所需包与接口、必要数据/权限/事务检查、完成条件及本次不做项。条件确认后保持稳定；新问题说明是否影响当前业务，必须扩范围时说明依据和代价，不默默把最终交付要求并入当前阶段。

先稳定当前业务必需的表、应用权限、约束、事务与启动，不要求所有业务表、完整清理、容量与恢复先做完才能隔离验证日报。这些仍是正式交付必需条件，各自保留并推进。依赖顺序用于当前业务内部，不能演变成全项目逐层开工。

## 怎样迁旧函数

| 旧实现 | 处理 |
|---|---|
| 正确、独立、只接收数据并返回计算结果 | 只迁当前业务需要的函数，放进本业务 `steps/` 内，由正式步骤调用 |
| 混着查库、Session、外部请求、计算与提交 | 拆开：读取与外部动作进 `store/`，计算进步骤，保存由新事务安排 |
| 重复、无用、本期不需要 | 不迁 |
| 已知错误或拆分比重写更贵 | 单独说明规则变化，按确认样例修复或重写 |

独立计算不能继续读全局配置、访问数据库、调用网络或暗中写文件。步骤声明输入输出字段，结果写回工作数据，计算仍纳入流程与运行记录。旧表独立定义在 `server/legacy/`，只由存储使用只读入口，不进入新库迁移。具体例子见 [日报迁移样板](references/report-example.md)。

## 共同验证与逐项替换

尽早把来源、计算、保存和旧接口放到一个共同版本验证，每次记录共同提交、迁移版本、配置、实际应用角色与输入来源。各包单独通过不能代替共同版本；数据库升级后旧版本证据过期。不展开长期分包开发再集中整合，不制造大量无人维护的分支与工作目录。

固定输入比较新旧结果，金额、单位、空值、缺失、边界与异常有明确预期；旧结果正确性另看业务规则。记录与确认可以替代真实外部写动作，但真实来源完整性和旧页面使用必须分别说明。

在 `server/` 比较两份 OpenAPI：

```bash
uv run python ../.agents/skills/fastapi-migration/scripts/run_migration.py compare_api --before /旧/openapi.json --after ../doc/api/openapi.json
```

接口比较只比较声明，不证明页面能用。接上旧页面，实际完成生成、查看与下载；占位返回未就绪不是已迁移。测试过期、错误数据库权限、测试配置缺能力先修测试安排，不能放宽金额、时间或权限规则。调价确认与商品占用等必须一起成功的动作保持同一事务；失败记录不能阻塞业务事务。

每项业务分别记录：已实现、共同检查通过、旧页面可用、已正式切换，并附当前版本和证据。还未获得真实来源、身份或环境的保持未验证，不写精确或估算迁移百分比。汇报先讲哪个用户操作能做、结果是什么、卡在哪里。

外部写操作在迁移期间只由一套系统执行，验证用替代服务；未知结果先查明，不重复写。正式切换前完成适用的容量、恢复、清理保护、权限与部署检查，写明切换与撤回办法，上线单独确认授权。完成第一项可用业务后再扩大范围。
