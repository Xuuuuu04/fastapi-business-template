# 业务迁移

## 目标和做法

每次迁完一项用户能检查、能使用的业务，并保留已经确认的行为。

- 默认由一个代理从头负责：理解业务、写代码、改数据库、做联合检查。只有用户或项目规则明确要求时才分给多个代理。
- 不清空已有成果，不整批搬函数，不把迁移变成全面重写。

## 开始一项业务

1. 先读 `.agents/records/business-state/模块名.md` 的生成摘要与手写业务判断/外部依赖/下一步；没有记录时用project business_state生成，运行未知不补成成功。再读旧系统里这项业务的入口、调用关系、规则、样例，以及新系统里已有的成果，并记下旧版本。
2. 列出用户的操作和对应的旧接口，选出最小的完整业务。例：经营日报 = 读取订单 → 计算 → 保存并发布 → 旧页面查看和下载。
3. 在现有任务记录里写清楚：
   - 数据从哪里来；
   - 应得的结果；
   - 页面上的操作；
   - 需要哪些业务包和接口；
   - 需要哪些数据、权限、事务检查；
   - 完成条件；
   - 这次不做什么。
4. 条件确认后保持稳定。中途发现新问题，说明它是否影响当前业务。确实要扩大范围，就讲清依据和代价，不要悄悄把最终交付的要求并进当前阶段。

先稳定当前业务必需的表、应用权限、约束、事务和启动。不需要等所有业务表、完整的数据清理、容量测试和恢复演练都做完，才开始验证这一项业务。这些仍是正式交付前必须完成的，各自保留并继续推进。

依赖顺序只用来安排这一项业务内部的工作，不能变成"全项目一层一层做"。

## 先搭整链，再逐阶段实现

迁移含定时或长流程的业务，先用 `new_pipeline` 登记完整链、Wait、定时首入口和演练占位，再按阶段补来源/计算/保存/发布。不要先把多个底层包做完才连流程，也不要把整段旧函数放进一个Stage。

```bash
uv run python ../.agents/skills/fastapi-module/scripts/run_module.py new_pipeline report daily --title 经营日报 --stages collect,wait,calculate,publish --wait wait
```

选择方法：短保存用普通`Flow(...steps=[validate, save])`，必须一起回滚；固定范围大量数据用`JobPlan(parse, segmented=True, repeat_safe=True, cursor=Cursor)`每批5000行推进Checkpoint；采集/等待/汇算/发布用`Pipeline(...Stage/Wait...)`，每阶段独立事务，汇算Stage内部可分段。完整声明片段与独立样例见[模块开发](../fastapi-module/SKILL.md)、[步骤与事务](../../../server/shared/flow/README.md)、[后台任务](../../../server/shared/jobs/README.md)。生成的正常样例只证明骨架，必须换成已确认的实际结果。

## 怎样处理旧函数

| 旧函数的情况 | 怎么处理 |
|---|---|
| 正确、独立，只接收数据并返回计算结果 | 只迁当前业务用到的函数，放进本业务的 `steps/`，由正式步骤调用 |
| 查库、用 Session、请求外部、计算、提交混在一起 | 拆开：读取和外部动作放 `store/`，计算放步骤，保存交给新的事务安排 |
| 重复、没用、这期不需要 | 不迁 |
| 已知有错，或拆开比重写还贵 | 单独说明规则有什么变化，按确认的样例修复或重写 |

迁进来的计算函数不能再读全局配置、访问数据库、调用网络或偷偷写文件。步骤声明输入和输出字段，结果写回流程的工作数据，这样计算仍然出现在流程图和运行记录里。

旧数据表单独定义在 `server/legacy/`，只通过存储里的只读入口使用，不放进新库的迁移。完整例子见 [日报迁移样板](references/report-example.md)。

## 数据导入计划与对账

恢复工具退出码0只说明命令正常结束，不能证明对象、行数、质量或来源完整。
先固定来源提交/快照编号、输入范围和不可重复的范围键，分别列出对象清单、业务行数、
金额等关键字段合计、质量字段最低非空率与引用关系。来源未知时保持未知，先补证据。
结构恢复和业务数据、质量、来源数据导入分开核对，不能把空库恢复算成功。

在 module.py 的现有JobPlan上登记（从 `shared.public` 导入）：

```python
import_plan = ImportPlan(
    source_revision="旧系统固定提交或快照编号",
    key="门店A-20261008-固定来源范围",
    reconcile=Reconcile(
        imported_rows,
        rows=10000,
        sums={"amount": Decimal("123456.78")},
        non_null={"quality": 1.0, "source_revision": 1.0},
        references=(ImportReference("parent_id", parent_rows.c.id),),
        where=imported_rows.c.import_key == "门店A-20261008-固定来源范围",
    ),
)
# JobPlan(load, segmented=True, repeat_safe=True, import_plan=import_plan)
```

目标与引用表登记在本模块tables；金额使用ExactNumber与Decimal。预期来自原件清单，
不能用导入后的数量反推预期。多来源分别登记计划与范围；where限定本次导入，
全表导入才省略where。非空率统计SQL非NULL；需要判断空串/业务有效性时增加正式规则步骤。
来源范围键和对账预期进入声明摘要及队列去重；同计划重复提交复用原任务，输入不同拒绝。

复用分段提交，每批只读写一段并声明checkpoint.advance，最后声明finish。框架在最后一批
提交前自动对账目标实际数据：行数精确相等、合计精确相等、最低非空率、非空引用完整。
未登记的指标仍是未验证，不默认替产品选择质量字段。对账不通过任务失败并撤销最后一批，
之前已提交的批次保留，运行报告记录每个指标预期与实测；对账尚未执行标未知。
确认来源为空才使用Reconcile(...rows=0, allow_empty=True)，不能为通过而改行数。

生成迁移前先登记表归属，方法见 [迁移说明](../../../server/migrations/README.md)。
旧产品先处理历史危险动作警告，之后开启APP_MIGRATION_STRICT；外部表只保留，
不属于本产品维护的表不能删除、改名或改类型。

## 联合验证

含定时或长流程的迁移，完成条件是：先用 `fastapi-operations drill` 在隔离库按真实规模打通从定时首入口到发布的整条链，再补局部细节。使用录下来的上游原始响应回放，不访问真实系统；记录每阶段耗时、实际行数、最慢SQL、内存峰值、是否需要人工，以及回放和未覆盖阶段。配置与命令见 [系统操作](../fastapi-operations/SKILL.md)。只有样例规模、模拟模型或未覆盖的外部写操作不能算真实业务已验收；原件来源未知时明确标未知。

尽早把数据来源、计算、保存和旧接口放在同一份代码里验证。每次记下：提交编号、迁移版本、配置、实际使用的应用角色、输入数据来源。

- 各个包单独通过，不能代替放在一起运行的结果。数据库升级后，之前的验证记录就过期了。
- 不要先长时间分包开发、最后集中合并，也不要建一堆没人维护的分支和工作目录。

## 比较新旧结果

- 用固定的输入比较新旧输出。金额、单位、空值、缺失值、边界、异常都要有明确预期。旧结果本身对不对，要看业务规则。
- 外部写操作可以用"记录并确认"代替真实写入来验证，但真实数据来源是否完整、旧页面能否使用，要分别说明。
- 比较两份 OpenAPI，在 `server/` 执行：

```bash
uv run python ../.agents/skills/fastapi-migration/scripts/run_migration.py compare_api --before /旧/openapi.json --after ../doc/api/openapi.json
```

接口比较只比较声明，不能证明页面能用。要把旧页面接上，真正完成生成、查看、下载。返回"未就绪"的占位接口不算已迁移。

- 测试过期、数据库权限错、测试配置缺功能：先修测试的安排，不能放宽金额、时间或权限规则。
- 必须一起成功的动作放在同一个事务里，例如调价确认和商品占用。记录失败的情况不能阻塞业务事务。

## 记录和汇报

每项业务分四个状态记录，并附当前版本和证据：

1. 已实现
2. 联合检查通过
3. 旧页面可用
4. 已正式切换

还没拿到真实数据来源、身份或环境的，保持"未验证"。不要写精确的或估算的迁移百分比。汇报先说：用户哪个操作现在能做、结果是什么、卡在哪里。

收工更新业务现状手写部分（业务判断、外部依赖、下一步）；授权确认当前DB后用 `project business_state --module 模块名 --runs` 刷新生成事实，没有DB证据则不加--runs并保持未知。生成与手写不混写；生成超过24小时或源码/依赖/声明变化检查报错，检查本身不自动刷新。记录仅本机，不代替真实产品交付。

## 正式切换

- 迁移期间，外部写操作只由一套系统执行；验证时用替代服务。结果不明的先查清楚，不要重复写。
- 切换前完成适用的容量、恢复、清理保护、权限和部署检查，写明怎么切换、怎么撤回。上线需要用户单独确认授权。
- 第一项业务可用之后，再扩大范围。
