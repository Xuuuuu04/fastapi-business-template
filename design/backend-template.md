# 后端模板设计

这份说明面向评估或维护本模板的工程师，解释为什么要把 FastAPI 单体后端设计成声明式模块、受控步骤读写、单一写事务起点和全链路中文运行记录，以及这些选择如何帮助人类审查者与 AI 协作者长期维护复杂业务。

## 要解决的核心矛盾

企业后端在持续迭代与多人（或多 Agent）协作中，最容易在四个地方失控：

1. **模块边界腐化**：业务赶进度时跨包直接连表、互相导入内部函数，改一张表牵动半个仓库。
2. **事务与外部调用混在一起**：在数据库写事务里夹杂慢速 HTTP 请求或大模型调用，既拖垮连接池，又在超时重试时造成重复扣款或重复通知。
3. **排错只能翻海量日志**：请求报错后看不出停在哪一步、前面读到了什么、有没有写进数据库。
4. **模板升级进退两难**：复制脚手架后框架与业务混改，上游修了并发或安全缺陷，下游产品根本没法合并。

本模板的做法是把这四类约束直接放进启动校验、AST 导入检查和执行器本身，让违规代码在本地启动或提交检查阶段立即暴露，业务开发者只需专注编写规则、数据含义和计算步骤。

## 三类包与单向依赖

仓库把代码严格分成框架层（`server/shared`、`server/app/setup`）和产品层（`server/service`、`server/library`）：

```
HTTP 路由 / 后台任务 / 定时计划
        │
        ▼
  流程包（workflow）  ── 只编排跨包流程，不建表，不调其他流程包
        │ uses=[能力包公开操作]
        ▼
  能力包（capability）── 独占本包数据表，跨包只允许读取已声明依赖的 query 操作
        │
        ▼
  纯工具包（library） ── 无状态纯计算，不连库、不发请求
```

- 业务包之间只允许导入对方的 `public.py`，不允许导入其他包的 `store`、`steps` 或 `data` 内部实现。
- SQLAlchemy Core 查询只允许出现在能力包的 `store/` 目录，禁止 ORM 隐式懒加载和手写原始 SQL 字符串。
- 带 `org_column()` 或 `owner_column()` 的多租户与负责人隔离表，由存储层在执行前逐层校验 `WHERE` 条件。

## 步骤声明与事务顺序

每个业务操作由三样东西组成：公开契约（`contract`）、工作数据（`WorkData`）和步骤序列（`Flow`）：

1. **读写字段显式隔离**：每个 `@step` 必须声明 `reads` 和 `writes`。执行器只把声明过的字段暴露给当前步骤；未声明的读取、越界修改、写入浮点数金额都会当场报错。
2. **先读、再调外部、最后写库**：没有标记 `saves=True` 的步骤默认使用只读连接。当流程进入第一个 `saves=True` 步骤时才开启写事务，此后禁止再发起外部 HTTP 请求或大模型调用；整条操作全部成功才提交，任一步失败整体回滚。
3. **查询与写入严格区分**：`effect="query"` 的操作禁止写库、登记任务、调用外部写接口或调用 `command` 操作。

## 外部副作用与后台任务安全

- **未知结果绝不盲目重发**：外部写接口（`effect="write"`）遇到超时、5xx 或断连时，框架统一归类为“结果待确认（`UNKNOWN_RESULT`）”，停止自动重发并记录原请求，交由业务查询核实后再处理。
- **数据库内置队列与分段推进**：后台任务、定时计划（`Schedule`）、多阶段流程（`Pipeline`）和并行拆分汇总（`FanOut`）直接基于数据库事务推进，无需额外部署消息队列。大批固定范围数据通过 `segmented=True` 按游标分批独立提交。
- **关键并发逻辑配有状态模型**：多个 worker 竞争领取与超时接管同一任务的并发协议，配有独立的 Python 状态枚举与 TLA+（`JobCommit.tla`）形式化规约，并绑定源码摘要防止实现偏离模型。

## 运行可观测与模板升级

- **每次运行自带结构化中文报告**：无论通过 HTTP 接口、后台任务还是命令行 `dev run` 触发，框架都会按 `run_id` 记录步骤耗时、慢步骤高亮、字段摘要、SQL 表名与行数，以及精确到文件行号的报错位置。本地可通过 `/system/console` 排查网页直接浏览调用图。
- **无共同 Git 历史的三方升级**：新产品初始化时在 `template-source.json` 记录受管框架文件的摘要。后续升级时，`dev upgrade` 对比旧模板、新模板与当前产品三份内容：产品未改的自动更新，改在不同位置的自动合并，改在同一位置的报告冲突并保持原文件不动，业务包与迁移历史完全不受覆盖。
