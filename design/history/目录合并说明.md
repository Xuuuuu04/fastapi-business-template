# 目录合并说明

## 1. 调整理由

根目录同时列出接口、数据库、日志和通知，会迫使阅读者一次辨认过多对象。本轮按查找目的合并到七个入口。app 和 service 分别回答“请求如何运行”和“业务做什么”；shared 集中有明确子分类的公共能力。


## 2. 旧新路径

按用户最新要求，业务层使用 service 命名。此前的 business/service 合并为 service，角色目录直接放在其下；business/data 移到 service/data。

| 原位置 | 新位置 |
| --- | --- |
| api | app/api |
| setup | app/setup |
| service | service |
| data | service/data |
| config | shared/config |
| db | shared/db |
| logs | shared/logs |
| login | shared/login |
| files | shared/files |
| jobs | shared/jobs |
| history | shared/history |
| notices | shared/notices |
| migrations | shared/db/migrations |

API 内的 docs、errors、replies、access、checks、limits、health 和 routes 全部保留。jobs、history、notices 仅搬到 shared，不删除其设计。

## 3. 与此前 core 的区别

shared 下只允许表中已明确职责的能力包。新功能先判断是否属于某个业务，不以“可能复用”为由放入公共目录。若同一包出现多个无关目的，应调整内部职责，而非继续增加不明确的总包。

层级用于导航；SOLID 仍需通过职责、依赖及替换行为验证。合并目录不会自动满足原则，也不改变现有依赖约定。

## 4. 本轮验证范围

检查所有文档链接、当前模板路径和目录搬迁是否完整；参考分析保留原项目路径。当前没有应用源码，未执行功能测试、数据库迁移或部署。
