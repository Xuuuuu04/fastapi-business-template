## 2. 数据怎样检查

按业务对象提供 README.md、models.py 和 examples。README 用中文解释含义、单位、缺失条件、维护方和状态；Python 类型定义字段与约束；JSON 合成样例展示正常和异常情况。

需要校验和序列化时可以采用 Pydantic，并从类型生成 JSON Schema；内部简单计算对象也可以用 dataclass。工具尚未安装，样例和生成流程尚未实现。

人类应能直接回答：这笔数据表示什么、谁可以改、空值意味着什么、哪些输入不合法。不人工维护多套相同的字段清单。

数据库表和查询放所属业务的 store；HTTP 输入输出放 app/api 的 forms.py；共享业务类型放 service/data。业务在 needs.py 中声明需要外部提供的操作。

## 3. SOLID 怎样检查

| 原则 | 简单说法 | 检查例子 |
| --- | --- | --- |
| S：单一职责 | 因同一类原因修改的代码放一起 | 改导出样式不必改统计公式 |
| O：开闭原则 | 已知变化可以通过增加实现支持 | 加一种导出方式，只增加实现并调整组装 |
| L：里氏替换 | 换实现仍遵守原有行为约定 | 两个读取实现对空值、排序和错误有相同约定 |
| I：接口隔离 | 只依赖自己需要的操作 | 只读报表无需依赖删除操作 |

service.py 组织业务，rules.py 计算，needs.py 说明所需操作，store 保存与查询。它们可以处于同一个业务包，不需要为了分层把业务文件散到全项目。

普通函数仍然使用普通函数，不为每个函数建立类或接口。目录本身不能证明满足 SOLID，实现后还需检查调用关系和替换行为。

## 4. 部署取舍

build 记录构建方式，env 记录环境差异，scripts 保存执行脚本，guides 解释操作步骤。同一构建产物配合不同环境配置使用。

数据库迁移仍归 shared/db/migrations。应用版本退回前核对数据库兼容性；数据恢复需要单独验证。部署方式尚待选择，目前不生成执行脚本。
