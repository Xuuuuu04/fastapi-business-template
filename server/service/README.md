# service：业务模块

每个子目录是一个业务模块，按“一个人能完整说清的业务能力”划分，例如“用户权限”“文件管理”。模块之间只通过操作约定互相调用。

从产品业务线到开发包的层次见 [项目设计](../../doc/development.md)，分组在根目录 `project-plan.json` 中填写。
代码保留统一模块路径，避免改变生成器、模块导入和已有产品。开发时用 `tools.project --module 模块名` 一次查看本模块的操作、条件分支、计算图、源码和最近测试情况。

## 每个模块的固定结构

```text
模块名/
├── README.md     用途、公开操作、依赖、内部组织、业务文档、测试
├── module.py     模块声明：操作与流程的对应、存储实现、表、提示词、任务
├── module.json   生成器写入的结构版本；不能自行扩展允许文件范围
├── public.py     其他模块和接口层唯一允许导入的文件
├── data.py       公开数据、流程数据、业务错误；每个字段都用 meaning() 写含义
│                 超过 300 行时按主题拆出 data_主题.py，写法相同
├── flow.py       把步骤按顺序连成流程
├── steps/        步骤，每个文件放一组相近的步骤
├── store/        contract.py 声明需要的读写，sql.py 实现，tables.py 定义表
└── prompts/      大模型提示词文件（需要时）
```

固定文件在每个模块中名字相同，读懂一个模块就能读懂所有模块。一个步骤对应一个可说明的业务动作；简单查询只用一个步骤，相近的小函数可以放在同一个文件，不为每次赋值拆步骤。

## 新建模块

```bash
uv run python -m tools.new_module customer_contact --title 客户联系人
```

它会生成完整骨架、业务文档、接口和测试，并登记到 `app/setup/catalog.py`。不要手工复制其他模块，也不要自己发明目录结构。生成器准备步骤测试、接口测试、权限与非法输入检查；真实业务的预期值仍须来自确认的规则。开发时运行 `uv run python -m tools.check --module customer_contact`，交付前运行全量检查。

默认服务与 worker 在创建资源前检查目录和登记、生成说明、文件位置、步骤函数位置、依赖方向和框架摘要。
不合格时拒绝启动，关闭模块不会跳过结构检查。包根不接受任意辅助文件；步骤和存储可增加一层 `.py` 文件，
`prompts/` 只接受 Markdown 或文本。旧项目先运行 `tools.adopt_modules`；全部包通过检查才写入结构说明。
这套检查发现意外偏离；同一账号的文件修改权限由开发环境控制，说明文件不证明创建者身份。

每个步骤是运行图的一个计算节点，直接显示函数、文件与行号、用时、实际产出的字段及其形状；
条件也有独立函数和时间。需要深入一个长计算时把它拆成可说明的步骤，短辅助函数时间包含在所属步骤中。
数据库通过 `Db` 自动记录 SQL 的表或视图、用时、行数、存储函数和调用行，不需要业务包自己添加计时。

## 必须遵守的规则

| 规则 | 原因 |
| --- | --- |
| 只从 `shared.public` 使用框架，只导入其他模块的 `public.py` | 模块内部可以随意重构，不影响别人 |
| 不导入 fastapi、httpx 等 HTTP 库；数据库库只在 `store/` 中使用 | HTTP 处理在 app/api，数据访问在 store，分别负责 |
| 每个字段写清含义，可空字段写清空值含义 | 人和 AI 都不用猜 |
| 计算规则写进 `doc/模块名/rules.md` 并编号，代码中用 `rule="R-xx"` 引用 | 字段来源能追到业务规则，业务变化时知道改哪里 |
| 表名以模块名开头，只由本模块读写 | 数据有唯一的所有者 |
| 存储实现的构造参数只用约定名称：`db` 本模块数据库、`legacy` 旧系统只读库、`remote` 外部接口、`files` 文件存储、`cache` 缓存、`caller` 调用者身份、`vault` 字段加密 | 框架按参数名注入，写错名称启动时报错；数据库连接只在需要 `db` 时打开 |
| 多组织数据的表用 `org_column()`，每层查询都写 `org_id == caller.org_id`；只给负责人看的数据用 `owner_column(see_all="权限")` | 漏写组织或负责人条件时数据库入口直接报错，不会串数据 |
| 需要追溯的修改用 `db.update_tracked`；先读后写用 `change_or_fail` 或 `first_for_update` | 谁改了什么可查；并发修改不会互相覆盖 |
| 一个流程最多 12 步，太长就拆成本模块的内部操作 | 一个人一次能看懂的范围有限 |
| 不写多余的防御代码，不吞掉异常 | 出错要在运行记录中看得见，不能悄悄变成空值或零 |
