# service：业务模块

当前没有预置的业务模块。新增模块用下面的生成命令。

每个子目录是能力包或流程包，模块之间只通过公开操作调用。能力包拥有领域数据和规则；跨领域写入由流程包编排，仍沿用同一事务。流程包可以保存批次、执行状态和结果引用。

`Module.kind`声明`capability`或`workflow`，公开操作用`effect="query"`或`effect="command"`声明性质。查询不能保存业务数据或登记任务，也不能调用写入或效果未知的操作。能力包跨包读取通过`read_dependencies`声明，依赖必须无环。省略类型的旧声明显示未知，不表示已经验证过。

跨业务纯函数、数据类型与协议解析放在[工具包](../library/README.md)，通过其`public.py`复用；步骤以`calcs`声明使用的计算。工具不能访问数据库、网络、文件、时钟和随机源。公开数据与关键流程字段应有明确类型，兼容原始输入模型通过`boundary_data`标记，不把任意字典显示为完整业务契约。

新建使用`uv run dev new-module customer_contact --title 客户联系 --kind capability`或`--kind workflow`；工具使用`uv run dev new-library text_formats --title 文本格式`。依赖始终来自声明和源码；包清单由生成器读取各包标记后生成。

代码保留统一的模块路径，避免改变生成器、模块导入和已有产品。开发时用 `uv run dev locate --query 模块名` 找到本模块的操作、步骤和源码位置。
开发按一项完整业务推进；迁移旧系统见[业务迁移 Skill](../../.agents/skills/fastapi-template/references/product-migration.md)。

## 每个模块的固定结构

```text
模块名/
├── README.md     用途、公开操作、依赖、内部组织、业务文档、测试
├── module.py     模块声明：操作与流程的对应、存储实现、表、提示词、任务
├── module.json   生成器写入的结构版本；不能自行扩展允许的文件范围
├── public.py     其他模块和接口层唯一允许导入的文件
├── data.py       公开数据、流程数据、业务错误；每个字段都用 meaning() 写含义
│                 超过 300 行时按主题拆出 data_主题.py，写法相同
├── flow.py       把步骤按顺序连成流程
├── steps/        步骤，每个文件放一组相近的步骤
├── calc/         可选：只接收参数、返回结果的纯计算
├── store/        contract.py 声明需要的读写，sql.py 实现，tables.py 定义表
└── prompts/      大模型提示词文件（需要时）
```

固定文件在每个模块中名字相同，所以读懂一个模块，就能读懂所有模块。一个步骤对应一个能说清楚的业务动作；简单查询只用一个步骤，相近的小函数可以放在同一个文件，不要为每次赋值单独拆步骤。

## 新建模块

```bash
uv run dev new-module customer_contact --title 客户联系人
```

它会生成完整骨架、业务文档、接口和测试，并登记到 `app/setup/catalog.py`。不要手工复制其他模块，也不要自己发明目录结构。生成器会准备步骤测试、接口测试、权限与非法输入检查；真实业务的预期值仍然必须来自确认过的规则。开发时运行 `uv run dev check --module customer_contact`，交付前运行完整检查。

默认情况下，服务和 worker 在创建任何资源之前会检查目录、登记、生成说明、文件位置、步骤函数位置、依赖方向和框架摘要。
不合格时拒绝启动；关闭模块也不会跳过结构检查。包根不接受任意的辅助文件；步骤和存储可以增加一层 `.py` 文件，
`prompts/` 只接受 Markdown 或文本。旧项目先运行 `uv run dev adopt-modules`；全部包通过检查后才写入结构说明。
这套检查用来发现意外的偏离；同一账号的文件修改权限由开发环境控制，说明文件不能证明创建者是谁。

每个步骤是运行图上的一个计算节点，直接显示函数、文件与行号、用时、实际产出的字段和它们的形状；
条件也有独立的函数和时间。需要深入一段长计算时，把它拆成能说清楚的步骤；短辅助函数的时间算在所属步骤里。
数据库通过 `Db` 自动记录 SQL 涉及的表或视图、用时、行数、存储函数和调用行，业务包不需要自己加计时。

## 必须遵守的规则

| 规则 | 原因 |
|---|---|
| 只从 `shared.public` 使用框架，只导入其他模块的 `public.py` | 模块内部可以随意重构，不影响别人 |
| 不导入 fastapi、httpx 等 HTTP 库；数据库库只在 `store/` 中使用 | HTTP 处理在 app/api，数据访问在 store，各管各的 |
| 每个字段写清含义，可空字段写清空值含义 | 人和 AI 都不用猜 |
| 表名以模块名开头，只由本模块读写 | 每份数据有唯一的所有者 |
| 存储实现的构造参数只用约定名称：`db` 本模块数据库、`legacy` 旧系统只读库、`remote` 外部接口、`files` 文件存储、`cache` 缓存、`caller` 调用者身份、`vault` 字段加密 | 框架按参数名注入，名字写错启动时就报错；数据库连接只在需要 `db` 时才打开 |
| 多组织数据的表用 `org_column()`，每层查询都写 `org_id == caller.org_id`；只给负责人看的数据用 `owner_column(see_all="权限")` | 漏写组织或负责人条件时，数据库入口直接报错，不会串数据 |
| 需要追溯的修改用 `db.update_tracked`；先读后写用 `change_or_fail` 或 `first_for_update` | 谁改了什么可以查；并发修改不会互相覆盖 |
| 一个流程最多 12 步，太长就拆成本模块的内部操作 | 一个人一次能看懂的范围有限 |
| 不写多余的防御代码，不吞掉异常 | 出错要在运行记录中看得见，不能悄悄变成空值或零 |

包内依赖：步骤（steps）可以使用 calc、data、store.contract；store 只依赖 store 和 calc；calc 只用本包 calc 和纯计算库。calc 不访问数据库、外部、文件、时钟或随机数；需要这些值时由步骤传进来，用 @step(calcs=[函数]) 登记。旧产品的反向导入默认警告，迁移完成后设置 APP_MODULE_DEPENDENCIES_STRICT=true；新生成的包默认严格检查，旧的结构说明仍然有效；新 calc 立即严格检查。详见 fastapi-module Skill。
